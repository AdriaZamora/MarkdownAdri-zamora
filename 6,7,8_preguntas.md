**5. a) Quina de les dues opcions és més ràpida d'escriure i més fàcil de llegir per a un humà quan s'obre el fitxer en un editor de text pla sense cap visor?**

L'Opció B (Markdown) és més ràpida d'escriure i més fàcil de llegir en un editor de text pla. Cada tasca ocupa una sola línia i no cal obrir ni tancar etiquetes. L'estat de la tasca es veu d'un cop d'ull amb [x] o [ ], i el text és gairebé una llista normal. En canvi, l'Opció A (XML) necessita escriure cada etiqueta dues vegades (obertura i tancament), té molts més caràcters i la informació queda amagada entre etiquetes i atributs, cosa que fa el fitxer més llarg i més pesat de llegir.

**5. b) Si l'Opció B és tan simple, per quina raó un sistema informàtic o una base de dades preferiria rebre/processar la informació en format XML (Opció A) quan s'envien dades entre servidors?**

Perquè XML és un format estructurat i no ambigu, pensat perquè les màquines el processin de forma fiable. Cada dada té un nom (tasca, descripcio, estat) i una posició clara dins la jerarquia, de manera que un programa pot llegir l'estat de la tasca sense interpretar text. En Markdown, [x] només és una convenció de format i no una dada amb significat propi. A més, XML es pot validar amb un esquema (XSD o DTD), de manera que el servidor receptor comprova que les dades tenen el format esperat i rebutja les que no. També és un estàndard d'intercanvi amb analitzadors (parsers) disponibles en tots els llenguatges, i permet representar dades complexes (nivells, atributs, llistes d'objectes) que Markdown no pot expressar bé. En resum, Markdown està pensat perquè una persona llegeixi i escrigui, i XML perquè dos sistemes s'entenguin sense errors d'interpretació.

**6. Per què creus que Markdown és l'estàndard dels README.md a GitHub?**

Perquè Markdown combina les característiques que necessita una documentació de projecte. És text pla, de manera que funciona amb Git sense problemes: es pot veure què ha canviat entre versions, fusionar canvis i revisar-los en un pull request, cosa que no és possible amb formats binaris. És lleuger i fàcil d'aprendre, perquè amb caràcters com #, * o - qualsevol persona pot escriure documentació en pocs minuts. Es llegeix bé fins i tot sense renderitzar. GitHub el renderitza automàticament a la portada del repositori, amb títols, llistes, taules, enllaços, imatges i blocs de codi amb colors. A més, és portable i independent del sistema operatiu i de l'editor, i es pot convertir a HTML, PDF i altres formats. Per tot això, Markdown s'ha convertit en el format de facto per a la documentació de programari.

**7. Imagina que estàs buscant una llibreria de codi a GitHub per al teu projecte. Quins beneficis té per a tu com a desenvolupador/a trobar la documentació en un fitxer README.md ben estructurat directament a la portada del repositori en lloc d'un fitxer adjunt en PDF o un document XML?**

Trobar la documentació en un README.md ben estructurat em dona accés immediat, perquè GitHub el mostra a la portada sense descarregar res ni obrir cap altre programa, i en pocs segons puc saber què fa la llibreria i si em serveix. Els títols, les llistes i les taules em permeten trobar ràpidament la instal·lació, els requisits o l'ús. Els blocs de codi amb ressaltat de sintaxi mostren exemples i ordres d'instal·lació que puc copiar directament, mentre que en un PDF això sovint dona problemes de format. Els enllaços i les imatges queden integrats al text. A més, el README viu dins del repositori, de manera que es modifica amb el codi i queda versionat, mentre que un PDF adjunt pot quedar desfasat. Finalment, és molt més fàcil de llegir que un XML, que està pensat per a màquines i està carregat d'etiquetes, i qualsevol persona pot proposar millores a la documentació editant text pla.

**8. Cas 1: Vols escriure els apunts d'un mòdul o la guia d'instal·lació del teu projecte perquè la llegeixin els teus companys de classe.**

Utilitzaria Markdown. Aquest text l'ha de llegir i escriure una persona, i Markdown permet fer-ho de forma ràpida amb títols, llistes, blocs de codi i enllaços, sense escriure etiquetes d'obertura i tancament. Es pot pujar a GitHub, on es visualitza formatat, i queda versionat. A més, és fàcil de llegir fins i tot en un editor de text pla.

**8. Cas 2: Vols crear un fitxer de configuració on una aplicació hagi de llegir les dades dels usuaris de forma estructurada.**

Utilitzaria XML. En aquest cas no importa tant la comoditat humana com que l'aplicació pugui processar les dades sense ambigüitats. XML defineix una estructura clara, amb noms per a cada dada (usuari, nom, correu) i jerarquia, que un programa pot llegir amb un analitzador (parser). A més, es pot validar amb un esquema (XSD o DTD) per assegurar que les dades tenen el format correcte abans de fer-les servir. Markdown no té estructura de dades: només indica com es mostra el text, així que l'aplicació no sabria quin valor correspon a cada camp.
